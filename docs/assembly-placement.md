# 数値配置と編集可能な `.blend` 受け渡し設計

## 文書の位置付け

この文書は、フェーズ4で平面部材を数値配置し、再生成可能かつBlenderで編集可能な組立モデルとして渡すための仕様正本である。対象は折りのない7部材の理想化3段棚であり、汎用CAD、拘束ソルバー、接合・強度保証、折り、両面印刷、納品レンダリングは扱わない。

記述は次の3種類を区別する。

- **確定要件**: ユーザー回答、親Issue、完了済みフェーズから継承する要件。
- **現行実装**: `cbcbc90e0dc23945ffe960ddc41598ca366a3077` 時点で確認できる事実。
- **フェーズ4設計**: このフェーズで採用する仕様。理想化サンプル固有の値は実案件仕様ではない。

## 範囲と成立条件

### 確定要件

- Illustratorで整理した切断形状・印刷・実寸から生成した複数の平面板を、部材ごとの数値で配置する。
- 棚位置は床から棚上面までの高さで指定でき、板厚との関係を検証する。
- 同じ入力から同じ配置を再生成できる。
- 保存後の `.blend` を再オープンし、形状、印刷、配置をBlenderで編集できる。
- 初期試作は折りなし、片面印刷、3段棚とトップボードを対象とする。
- 形状・寸法改訂時は新規生成する。生成後の手編集を改訂へ自動追従させない。
- 長期的には人のUI操作とAI/CLI操作の両方から同じ明示入力を扱えるようにする。ただしフェーズ4ではCLIを実行入口とし、専用UIやMCPを必須にしない。

### 現行実装

- 入力束はIllustrator書き出し `export.json`、表面画像 `print-front.png`、外部指定の紙厚からなる。
- `three-shelf` は `SIDE_LEFT`、`SIDE_RIGHT`、`SHELF_01`〜`03`、`BACK`、`TOP` の7部材である。
- 各部材は閉じた編集可能meshで、局所原点は `placement_bounds_mm` の左上、局所 `+X` はアートボード右、局所 `+Y` はアートボード上、局所 `+Z` は印刷面である。形状は局所原点から `+X` と `-Y` 側に広がる。
- 厚み中心は局所 `Z=0`、印刷面は `+thickness/2`、裏面は `-thickness/2` である。
- Blender内部では1 mmを0.001 Blender unitに変換する。sceneはmetric/millimeters表示である。
- 表面画像は `.blend` からの相対パスで外部リンクされる。現成果物はリポジトリ一式を保って開く契約である。

### フェーズ4の完了条件

配置入力、入力検査、平面板生成、配置、保存、再オープン検証を一つの再現可能なCLI経路で実行できることを完了条件とする。7部材すべてについて、参照元、変換、基準面、期待するワールド境界をmanifestに残す。Blender上でオブジェクトのtransformとmeshを編集でき、画像リンクが解決することを再オープン後に確認する。

## 利用者の作業フロー

1. 利用者はIllustrator入力を既存規約で整理し、書き出し束を作る。紙厚を明示する。
2. 利用者は仕様書や完成写真を参照し、部材instanceごとの位置・向きと、棚上面など検査対象の基準面値を配置入力へ記す。写真からの自動推定はしない。
3. CLIは配置入力と書き出し束を先に検査する。未知の部材参照、重複instance ID、不正な単位・回転、非有限値、期待基準面の不一致があれば生成前に失敗する。
4. CLIは既存と同じ局所mesh・UV・材質を生成し、instanceごとにワールド変換を適用する。
5. CLIは `.blend`、相対参照画像、manifest、検証report、確認用画像を一つの成果物ディレクトリへ出す。
6. 別プロセスで `.blend` を再オープンして自動検証する。利用者は斜俯瞰と補助視点で印刷方向、部材の取り違え、隙間・交差、全体の見た目を確認する。
7. 配置値を直す場合は配置入力を修正して別出力へ再生成する。納品調整などの手編集は生成物上で行えるが、再生成時には保持されない。

人が決めるのは完成形の意図、仕様書から読む数値、未確定の接合基準、最終外観である。CLIが担うのは検査、決定論的な変換、保存、機械検証、証跡生成である。AIは同じ配置入力を作成・修正しCLIを呼べるが、会話履歴を配置の正本にしない。

## 入力の正本と成果物

### 配置入力

配置の正本は、生成物と別に版管理できる単一の機械可読ファイルとする。初期実装は既存処理と同じJSONを推奨する。JSON自体はユーザーが確定した製品要件ではなく、CLI・検証・将来のUI/AIが同じ契約を共有しやすいという実装選択である。

最低限、次を持つ。

```json
{
  "schema_version": "0.1",
  "status": "idealized-prototype-not-production-specification",
  "unit": "mm",
  "world": {
    "origin": "floor, back mid-plane, left inner face",
    "x_axis": "right",
    "y_axis": "back",
    "z_axis": "up",
    "rotation_mode": "XYZ extrinsic degrees"
  },
  "sources": {
    "panels": "build/illustrator-export-r2/three-shelf/export.json",
    "print_front": "build/illustrator-export-r2/three-shelf/print-front.png"
  },
  "instances": [
    {
      "id": "shelf-01",
      "part_id": "SHELF_01",
      "translation_mm": [0, -1.5, 118.5],
      "rotation_deg_xyz": [0, 0, 0]
    }
  ],
  "checks": {
    "shelf_top_heights_mm": {
      "shelf-01": 120,
      "shelf-02": 240,
      "shelf-03": 360
    }
  }
}
```

回転の曖昧さを避けるため、ファイル上は度、軸順 `XYZ`、固定ワールド軸に順に適用する外因性回転として定義する。実装はこの定義から3×3行列またはquaternionを一度生成し、BlenderのEuler解釈を暗黙に正本としない。manifestには解決後の4×4行列を記録する。平行移動は部材局所原点を移すワールド座標である。scaleは入力させず常に1とし、寸法変更は上流形状の改訂とする。

`part_id` は形状・UV・材料を持つ部材定義への参照、`id` は配置されたinstanceの安定IDである。同じ `part_id` を異なる `id` から複数回参照できる。この分離により、同一棚板の反復配置を複製meshとして編集可能にしながら、参照元を追跡できる。初期実装ではinstanceごとに独立mesh dataを持たせ、Blenderで一枚だけ形状編集しても他instanceへ波及しないようにする。リンク複製はファイルを小さくできるが、利用者に共有meshの編集挙動を要求するため採用しない。

### 正本の境界

- 切断形状、部材ID、UV座標、印刷範囲の正本は既存 `export.json` と画像である。
- 紙厚の正本は既存の外部材料入力である。
- instance、ワールド変換、配置検査値の正本は配置入力である。
- `.blend`、manifest、report、previewは派生成果物である。
- 理想化サンプルの寸法と高さは試作検証値であり、実案件の正本ではない。

配置入力は上流ファイルをリポジトリ相対パスで参照し、生成時に各入力のSHA-256をmanifestへ保存する。相対パスがリポジトリ外へ脱出する入力は拒否する。これにより別checkoutでも同じ構成を扱い、絶対ローカルパスを成果物へ残さない。

### 受け渡しと画像

成果物ディレクトリは少なくとも次を含む。

```text
assembly/
  assembly.blend
  textures/print-front.png
  build-manifest.json
  verification.json
  preview-perspective.png
  preview-reference.png
```

フェーズ3のリポジトリ相対リンクはcheckout内で成立するが、`.blend` と離れた上流build treeの同伴が必要になる。フェーズ4では入力画像を内容を変えず `textures/` へコピーし、`.blend` から `//textures/print-front.png` で参照する方式を採用する。元画像とコピーのhash一致を生成時と再オープン後に検査する。画像をpackする案は単一ファイル受け渡しに強いが、画像差し替えとhash検証が見えにくくなるため初期採用しない。`.blend` 単体ではなく成果物ディレクトリ全体を渡す。

## 座標系と基準面

### ワールド座標

- 原点: 床面、左右側板の内側に接する公称左端、背面中心面の交点。
- `+X`: 正面から見て右。
- `+Y`: 正面から奥。
- `+Z`: 上。
- 単位: 入出力はmm。Blender transformへ設定するときだけ0.001倍する。

基準が材料の外面・中心面・内面のどれかは配置入力とchecksで明示する。理想化サンプルでは、360 mmを棚・背面の幅かつ左右側板の内寸、背面中心面を奥行基準とする。この解釈は既存サンプル値から組立を成立させるフェーズ4の推奨であり、ユーザーの実案件仕様ではない。

### 部材局所座標

既存の部材局所座標と厚み中心は変更しない。配置は次式で一意に定める。

```text
p_world_mm = translation_mm + R(rotation_deg_xyz) × p_local_mm
```

局所meshを移動・回転して作り直さず、オブジェクトtransformとして保存する。これにより局所寸法・UV・印刷面法線を既存検証と共用でき、利用者もBlenderのLocation/Rotationから配置を編集できる。適用済みtransformで頂点へ焼き込む案は数値の追跡と手編集を難しくするため採用しない。

### 棚上面と厚み

水平棚は局所回転 `[0, 0, 0]` とし、局所 `+Z` の印刷面を上面にする。厚み `t`、要求上面高さ `H` のとき、局所原点のワールドZは次式である。

```text
translation_z = H - t / 2
bottom_z = H - t
top_z = H
```

3 mm厚で上面120 mmなら、原点/厚み中心は118.5 mm、下面は117 mmになる。上面高さをオブジェクト原点へ直接設定する実装は1.5 mm高くなるため不正である。

## 理想化3段棚の具体配置

### 入力値と暫定仮定

確定している試作値は次の通りである。

| 部材 | 寸法 mm | 枚数 |
| --- | ---: | ---: |
| `SIDE_LEFT`, `SIDE_RIGHT` | 300 × 460 | 各1 |
| `SHELF_01`〜`03` | 360 × 260 | 各1 |
| `BACK` | 360 × 460 | 1 |
| `TOP` | 360 × 270 | 1 |

厚みは3 mm、棚上面は床から120 / 240 / 360 mmである。これらは理想化試作値である。

配置例では次を暫定推奨とする。

- 背面中心面を `Y=0` とする。360 mmを棚・背面の幅かつ側板内寸とし、側板の内面を `X=0` と `X=360` に置く。側板中心面間は363 mm、左右各3 mmの厚みを含む外幅は `363 - (-3) = 366` mmとなる。
- 棚の奥端を背面の正面側表面 `Y=-1.5`、前端を `Y=-261.5` に置く。
- 300 mm奥行の側板は背面の正面側表面から `Y=-301.5` まで伸ばし、棚より前へ40 mm出す。
- `TOP` は水平天板と仮定し、奥端 `Y=-1.5`、前端 `Y=-271.5`、上面 `Z=460` に置く。
- 印刷は棚・天板で上、背面で正面（`-Y`）、左右側板でそれぞれ外側を向ける。

トップボードが垂直ヘッダーを意味する場合、この例のTOP配置は採用できない。用途はユーザー判断が必要である。

### 解決後の配置

以下は説明用の回転行列が表す局所軸の向きであり、実装は前述の共通回転定義から解決する。

| instance | rotation deg XYZ | 局所軸のワールド向き `(X,Y,Z)` | translation mm | ワールド範囲 mm |
| --- | ---: | --- | ---: | --- |
| `side-left` | `(90,0,-90)` | `(-Y,+Z,-X)` | `(-1.5,-1.5,460)` | X `-3..0`, Y `-301.5..-1.5`, Z `0..460` |
| `side-right` | `(90,0,90)` | `(+Y,+Z,+X)` | `(361.5,-301.5,460)` | X `360..363`, Y `-301.5..-1.5`, Z `0..460` |
| `shelf-01` | `(0,0,0)` | `(+X,+Y,+Z)` | `(0,-1.5,118.5)` | X `0..360`, Y `-261.5..-1.5`, Z `117..120` |
| `shelf-02` | `(0,0,0)` | `(+X,+Y,+Z)` | `(0,-1.5,238.5)` | X `0..360`, Y `-261.5..-1.5`, Z `237..240` |
| `shelf-03` | `(0,0,0)` | `(+X,+Y,+Z)` | `(0,-1.5,358.5)` | X `0..360`, Y `-261.5..-1.5`, Z `357..360` |
| `back` | `(90,0,0)` | `(+X,+Z,-Y)` | `(0,0,460)` | X `0..360`, Y `-1.5..1.5`, Z `0..460` |
| `top`（水平仮定） | `(0,0,0)` | `(+X,+Y,+Z)` | `(0,-1.5,458.5)` | X `0..360`, Y `-271.5..-1.5`, Z `457..460` |

側板と背面の縦方向では、局所形状が `-Y` に伸びるため、局所 `Y` 軸をワールド `+Z` に向けて局所原点を上端へ置く。左側板の印刷面は `-X`、右側板は `+X`、背面は `-Y` を向く。棚と水平TOPは形状が局所 `-Y` に伸びるので、局所原点を奥端 `Y=-1.5` に置く。

### 数値検算

各棚は `translation_z + 3/2` が120 / 240 / 360 mmとなり、指定上面に一致する。下面は117 / 237 / 357 mmである。棚間の鉛直空きは、下段上面から次段下面まで117 mmである。最上段上面360 mmから仮定したTOP下面457 mmまで97 mm空く。側板・背面の床端は0 mm、上端は460 mmである。

棚と背面の幅360 mmを左右側板の内寸として扱うため、棚端・背面端は側板内面へ面接触する。左側板のAABBはX `-3..0`、右側板は `360..363` なので、側板中心面は `-1.5` と `361.5`、中心面間は363 mm、組立全体のX外寸は `363 - (-3) = 366` mmである。棚とTOPの奥端は背面正面へ面接触する。理想的な直方体の境界では体積交差も隙間もない。曲線分割や浮動小数点誤差を考慮した接触許容差は実装Issueで決める。差し込み、糊代、板厚逃げ、製造公差は表現しないため、強度や製造可能性の検証結果ではない。

別案として360 mmを側板中心面間にすると棚端が各側板へ1.5 mm交差し、360 mmを外寸にすると内寸が357 mmとなり棚・背面の寸法改訂が必要になる。意図しない交差を正当化せず、既存の360 mm棚・背面を保って単純な面接触を作れる内寸解釈を採用する。将来サンプルを外寸360 mmへ合わせる場合は、棚・背面幅を357 mmへ明示的に改訂し、上流入力から再生成する。

## 再生成と失敗時の挙動

- 同じ入力内容、同じBlender 5.2.1、同じ曲線分割設定から、同じ部材ID、instance ID、変換、材質割当、画像hashを得る。`.blend` のバイナリhash一致はBlender内部の保存差を含み得るため受入条件にしない。
- 出力先が存在しない、またはツール自身が作ったmanifestと一致する場合だけ生成する。既存の手編集済み `.blend` がある、未知ファイルがある、入力hashが変わった場合は無言で上書きせず非0終了する。明示的な別出力または `--force` を利用者が選ぶ。
- 生成途中は一時成果物へ保存し、全検査成功後に成果物名へ置く。失敗した生成物を成功成果物として残さない。
- 入力検査エラーにはJSONフィールド、instance ID、part ID、期待値と実値を含める。複数の独立エラーは可能な範囲でまとめて返す。
- 参照部材欠落、重複ID、未知フィールド、非有限値、単位不一致、scale指定、回転定義不一致、画像hash不一致、要求基準面の許容差超過はhard failureとする。
- 接触・交差は接合仕様がない間はreportへ分類して記録する。期待した面接触は配置入力の許可リストで明示し、予期しない部材同士の体積交差はhard failureとする。微小な接触を数値誤差で失敗させない許容差を実装Issueで固定する。
- previewレンダリングだけの失敗と形状・配置検証失敗を区別して報告する。検証失敗時はCLIを非0終了させる。

## 検証戦略

### 自動検証

生成直後と保存再オープン後に次を検査する。

- schema、単位、参照パス、入力hash、部材/instance IDの一意性。
- 7instanceの存在、meshであること、編集可能であること、参照 `part_id` とobject custom propertyの一致。
- 各objectのtranslation、解決済みrotation matrix、scale=1。比較はmm空間の許容差で行う。
- 変換後の8つの局所bounding-box角から求めたワールド境界。
- 棚上面120 / 240 / 360 mm、下面117 / 237 / 357 mm。高さ検査はobject originではなく変換後meshの最大Zで行う。
- 側板・背面の床端0 mm、上端460 mm、棚奥端-1.5 mm、前端-261.5 mm、側板中心面間363 mm、組立外幅366 mm。
- 印刷面のワールド法線。棚/TOPは `+Z`、背面は `-Y`、左側板は `-X`、右側板は `+X`。
- フェーズ3から継承するclosed manifold、厚み、外形、穴、front/back/edge材質、UV。
- 画像相対パスが成果物ディレクトリ内へ解決し、コピー元とhashが一致すること。
- 許可した面接触と予期しない体積交差の分類。
- manifestにBlender版、入力hash、配置入力、解決行列、検証結果が揃うこと。

負例は少なくとも、棚高さを厚み中心へ誤設定した1.5 mmずれ、未知part、重複instance ID、画像欠落、scale指定、予期しない回転、未許可の大交差を用意し、非0終了を確認する。

### 人・実機での確認

- Blender 5.2.1で成果物ディレクトリを別の場所へ移し、`.blend` を再オープンしてmissing textureがないことを確認する。
- object transformとmeshが編集でき、保存後に再度開けることを確認する。
- 正面斜俯瞰、背面、左右、上下の補助視点で、青帯と矢印から表裏・上下・左右の反転を確認する。
- 7部材、3段の順序、40 mmの側板前出、端部の面接触、穴の向きを確認する。
- 製造接合の正しさではなく、指定数値に基づく外観配置として承認する。

1920×1080の納品想定外観と作業時間評価は次フェーズの範囲である。フェーズ4のpreviewは配置確認用であり、照明・背景・納品品質を完了条件にしない。

## 主要な代替案と選択理由

| 論点 | 採用 | 見送る案と理由 |
| --- | --- | --- |
| 正本 | 外部の配置JSON | `.blend`だけを正本にすると再生成・CLI/AI操作・差分レビューが難しい。会話履歴は再現不能。 |
| 配置表現 | instanceごとの絶対transform | 親子階層や相対移動は順序依存を持ち、折りなし7部材には不要。拘束solverは過剰。 |
| 基準 | 既存局所原点と厚み中心を維持 | mesh原点の付け替えや頂点へのtransform適用は既存UV/検証と数値追跡を複雑にする。 |
| 棚高さ | 要求上面から厚み中心を導出 | object originを上面とみなすと厚みの半分だけずれる。下面基準は利用者の仕様書と一致しない。 |
| 同一部材 | 定義参照 + 独立mesh instance | linked meshは個別編集時に他instanceへ波及する。完全複製だけでは参照元追跡が弱い。 |
| 画像 | 成果物内にコピーして相対リンク | repo全体同伴は受け渡しが重い。packは画像差替えとhash照合が見えにくい。 |
| 再生成 | 新規/明示上書き、手編集は追従しない | 自動mergeは何を保持するか決められず、初期範囲を大きく超える。 |
| 接触判定 | 期待する面接触を明示し、体積交差を検出 | 自動スナップは接合意図を推測する。接触検査なしでは寸法や回転の誤りを見逃す。 |

## 暫定決定と未決質問

フェーズ4の実装を進めるための暫定決定は、ワールド軸、既存局所座標の維持、絶対transform、棚上面から厚み中心への変換、instance/part分離、成果物内の相対画像、再生成時に手編集を保持しないことである。

次は製品上の判断が必要であり、回答を実案件仕様またはサンプル配置へ反映する。回答前に実案件の確定事項として扱わない。

1. `TOP` 360 × 270 mmは、上面460 mmの水平天板か、背面上部などに立つ垂直トップボードか。推奨仮定は、側板・背面の高さ460 mmと近い奥行270 mmを根拠に水平天板とする。水平天板なら上面460 mm、背面正面揃えとする。

幅はフェーズ4サンプルの設計値なので、利用者への追加質問にせず内寸360 mmを採用する。将来の実案件では配置入力に内面・外面・中心面のどの基準かを明記し、同じ規則で数値検査する。

## 実装Issue分割案

### 1. 配置入力契約と検査を実装する

目的は、part参照、instance、ワールド座標、絶対transform、棚上面checksを機械可読な正本として読み、生成前に診断すること。受入条件はschema/単位/軸/回転定義、参照・ID一意性、有限値、scale禁止、リポジトリ相対入力、7部材サンプルと負例の検査である。依存は本設計PR。対象外はBlender生成、UI、CAD拘束、実案件値の確定。検証は純粋Pythonの正例/負例と、解決済み行列・棚中心高さの比較で行う。

### 2. 既存平面板生成にinstance配置と成果物bundleを統合する

目的は、検証済みの局所meshをinstanceごとに生成し、object transform、custom property、相対画像を持つ編集可能な `assembly.blend` を保存すること。受入条件は同一part複数instance、独立mesh data、scale=1、画像コピー/hash、入力を壊さない再生成、既存出力の安全な扱い、manifestの入力hash/行列/版記録である。依存はIssue 1。対象外は再オープン検証、納品カメラ、手編集merge。検証はBlender 5.2.1で7部材生成と同一参照複数配置のfixtureを生成する。

### 3. 配置・基準面・保存再オープン検証を実装する

目的は、別Blenderプロセスで成果物を開き、形状と配置の両方を自動判定すること。受入条件はワールド境界、棚上下面、床端、印刷面法線、scale、instance参照、フェーズ3の形状/材質/UV/穴、相対画像、manifestを検査し、失敗時に非0終了すること。依存はIssue 2。対象外は外観の美的評価と製造強度。検証は3段棚正例、1.5 mm高さずれを含む負例、画像欠落、未許可交差を実行する。

### 4. 3段棚の配置証跡と利用手順を整備する

目的は、理想化7部材を再生成し、別場所への成果物移動、再オープン、Blender手編集までを人が追試できる形にすること。受入条件は配置入力、manifest、verification、確認用preview、README手順、確定要件/試作仮定/未決回答の反映、Blender 5.2.1実機記録である。依存はIssue 3と、TOP用途について必要なユーザー判断。対象外は1920×1080納品レンダリング、作業時間目標、実案件の製造保証。検証は自動reportに加え、人が前後左右・印刷方向・編集保存を確認する。
